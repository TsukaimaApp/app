## v0.2.0 rulings (clarify picker + attachments)

- Ruling: "Skip" on a clarify card replies `{}`, not `{"answers": null}` — the contract's `ClarifyResult` says a response without `answers` is cancel-all, the TUI's Esc path sends `{}`, and `server_requests.resolve` treats `{"answers": null}` as outcome `submitted` (empty), not `cancelled` — cost if wrong: one constant.
- Ruling: multi-select answers are `JSON.stringify([...picked, other])` (compact JSON array string), empty → null — ui-tui `prompts.tsx lockPicked` — cost if wrong: the agent sees a JSON string instead of a list.
- Ruling: a clarify with no askable question (no qid/question text) is cancelled at once in `ServerRequestRouter` with `{}`, as the TUI does, instead of leaving the agent waiting 300 s.
- Ruling: clarify notifications have no buttons (tap opens the asking chat) and are not tracked in `postedApprovals`, so a background disconnect does not cancel them (the tap resumes the chat, which re-adopts the open request).
- Ruling: attachment cap is 12 MB, not 16 MB — the bytes travel base64-encoded in one WebSocket text frame, and OkHttp's `RealWebSocket` closes the socket when a send would push its queue past 16 MiB (16 MB → ~21.3 MB base64). Server caps are higher (images 25 MB, WS frame 384 MiB). Toast "File too large (max 12 MB)" — cost if wrong: users cannot attach 12–16 MB files.
- Ruling: prompt text with file refs follows Hermes desktop `buildContextText`: refs joined by "\n", a blank line, then the typed text (`@file:a\n\nhi`), not text-first — cost if wrong: refs ordering only (both resolve).
- Ruling: Send is held while any upload is in flight — an image queued after `prompt.submit` would silently ride along with the next turn instead.
- Ruling: images are those Hermes can queue (png/jpeg/gif/webp/bmp by MIME); anything else (HEIC included) is uploaded with `file.attach`. The image filename gets a matching extension, since the server picks the type from the suffix.
- Ruling: an image removed while still uploading is detached as soon as its upload lands.
- v0.2.0 review fixes: uploads run one at a time (`ChatAttachments.uploads` mutex) so two frames can never exceed OkHttp's 16 MiB send queue; a resume that yields a new live session id marks queued (Ready) image chips Failed, since the old session's image queue is gone — retry re-queues them. Deferred (low confidence): a retry after a lost `image.attach_bytes` response can leave two copies queued server-side.
- HTTPS fronts: the dashboard names its cookies `__Host-hermes_session_at` behind TLS; `HermesApi.parseSessionCookie` accepts the `__Host-`/`__Secure-` prefixes (v0.1.x refused HTTPS logins).

## v0.3.0 rulings (`MEDIA:` file cards)

- Ruling: a `MEDIA:` line becomes a card only as a whole line outside code fences and bullets (TUI rule); the directive may be wrapped in a backtick/quote, the path may be backticked/quoted (spaces allowed), and an unquoted path may hold spaces only when it ends in a `MEDIA_DELIVERY_EXTS` extension (desktop's anchored branch). Only `/…` and `~/…` paths count: a relative or Windows path stays prose — the server answers 400 for relative paths anyway — cost if wrong: such a line shows as text.
- Ruling: while a reply streams, its last line is never a directive (a half-streamed path would flash a card for a non-existent file); a line ended by `\n` converts at once.
- Ruling: downloads use a client derived from the REST client with no call timeout (30 s read timeout between bytes) — the shared 20 s call timeout spans the body and would cut large files short. Same interceptors (bearer + re-login), same pool.
- Ruling: 400 maps to "Not a file" only when the server's detail says so (or is absent); other 400s (`Path must be absolute`, `..`) and 409 (live SQLite file) show the server's detail. 404/403/413 use the brief's fixed messages.
- Ruling: `FileSaver.save` returns the content uri as a `String` and `ChatBackend.openFile(uri: String, mime)` takes one — `android.net.Uri` cannot be built in JVM unit tests (stubbed android.jar), and the VM only passes it through.
- Ruling: previews cache definitive outcomes (bitmap, or none: too big, undecodable, server refusal) in an 8-entry LRU; a dropped connection or auth failure is not cached, so the card's next composition retries. Concurrent callers share one fetch. A preview is a full extra `GET` of the file (≤ 10 MB) — there is no thumbnail endpoint.
- Ruling: after "Saved to Downloads" the app always tries `ACTION_VIEW`; if no app handles the type, the toast is all the user gets (the file is in Downloads).

## v0.4.0 rulings (Tier 1 of the completeness pass)

- Ruling: Stop shows while the status is Thinking / Tool / Replying (`AgentStatus.running`), not while the turn waits for the user (approval, question, password) — the card is the way forward there. It replaces send in the same 44 dp slot as a danger-filled square; Enter does nothing meanwhile. The overflow menu also gets "Stop" (hidden offline). The turn's end is left to the server: live probe — `session.interrupt` answered `{"status":"interrupted"}` and the turn ended with `message.complete {text:"", status:"interrupted", persisted_turn:{complete:false,…}}`, which the reducer already treats as a normal end (partial bubble kept, Idle). An idle session also answers `interrupted`, so the "Nothing to stop" toast (for `not_interrupted`) fires only on Hermes's hosted-task mismatch — cost if wrong: a Stop on an idle chat is silent.
- Ruling: masked prompts (`sudo`, `secret`, `vault.unlock_prompt`) are forwarded like clarify; `vault.save_login` and `vault.code` stay "method not found" (they need a JSON identifier+password form and a 2FA flow — out of Tier 1). The value lives only in the card's `remember` state (not `rememberSaveable`, so it never reaches the saved-state bundle; a rotation clears the field) and is cleared on Send; `ChatItem.SecretPrompt` records only `answered`/`declined`. A send that was not enqueued re-opens the card with the field empty (the user retypes) rather than keeping the value — cost if wrong: one retype.
- Ruling: masked-prompt notifications ("Hermes needs a password" for `sudo`/`vault.unlock_prompt`, "Hermes needs a secret" for `secret`) carry the subject (command / env var / manager name) through `CommandText.reveal`, capped at 120, on the private approvals channel, content intent to the asking chat only — no `RemoteInput`, since a reply typed into the shade would pass through the notification system and its history.
- Ruling: status priority while several requests wait is Approval, then the latest masked prompt, then Question.
- Ruling: approval scopes come from `choices` when present, else derived like `tui_gateway/server.py::_approval_request_payload` (`session` unless `smart_denied` or `allow_session == false`; `always` additionally unless `allow_permanent == false`). "Approve for…" is a caption-sized accent text button left of Deny/Approve, disabled while the command is collapsed with hidden lines (same S5 rule as Approve). `ChatUiState.decisions` now holds the `ApprovalChoice` sent, so the answered caption names the scope. A scope the card does not offer is ignored by `answerApproval` (defence against a stale sheet).
- Ruling: sign-out keeps the poll loop: `ConnectionManager.signOut()` stops (bumping the generation, so an in-flight iteration cannot reconnect) and restarts the loop at the same interval if it was running. Polling the public `/api/status` continues, and with no stored password the gateway stays down — so a sign-in from the same foreground session connects at once without a lifecycle restart. The brief said "stops polling"; a full stop would strand the next sign-in until the app was backgrounded and foregrounded — cost if wrong: one status poll per 20 s while signed out in the foreground. Sign-out also clears `onboarded` (next launch starts at Onboarding) and `lastSessionId`; the URL and username stay to prefill the form. `navigateTop` now pops the whole graph when rebuilding Status, so the post-sign-out Onboarding → Settings stack does not linger under Status after the next sign-in.
- Ruling: a profile switch in Settings clears `modelProvider` with `model` (it had kept a stale provider, the same bug as the model picker).
- Ruling: the replay watermark starts at `NO_SEQ = -1`, not 0 (an event numbered 0 is applied; `session.events.since(last_seen = -1)` is valid — the server compares `seq > last_seen`). Hermes's own numbering starts at 1 (`event_replay.py`), so this is defensive.
- Ruling: `message.interim` with `already_streamed: false` closes the streaming bubble and appends the text as a completed reply (`i-<seq>`); into a still-empty reasoning-only bubble it is written in place (the reasoning stays attached). `already_streamed: true` and blank text are ignored.
- Ruling (live probe, item 10): a resume of a running turn returns `running: true`, `status: "working"`, `messages` with only the turn's user row, and `inflight {assistant, streaming, user}` whose `assistant` is the concatenation of every `message.delta` of the turn so far (1396 chars in the probe; `session_history._append_inflight_delta`). `session.events.since(0)` was `truncated` (the 512-event ring was mostly `reasoning.delta`s) and held only part of the deltas, so it cannot rebuild the partial reply. So a rebuilt transcript (`ChatSync.transcript`: first open, a new live id, or a truncated replay) appends `inflight.assistant` as a streaming bubble (`a-inflight`) when `running`; live `message.delta`s continue it. A same-live reconnect with an untruncated replay keeps using `events.since(lastSeq)` as before. Known gap: on the truncated-replay path, deltas emitted between the resume snapshot and the replay call are below the new watermark and not in the snapshot — a few characters can be missing until `message.complete` replaces the bubble's text with the final reply. If `inflight.assistant` spans several segments of a turn with tool calls, the bubble shows them run together until `message.complete`.
